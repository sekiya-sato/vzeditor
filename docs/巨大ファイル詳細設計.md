# 巨大ファイル対応 詳細設計

この文書は巨大ファイル対応の詳細設計で、**確定**と**案（要確認）**を分けて書く。実装の状況と設計から変えたところは 11 章。入力は次の 2 つ。
- Crowley "Data Structures for Text Sequences"（1998）: ピーステーブルの論文。
- vis のピースチェーン（wiki "Text management using a piece chain" と `text.c`、ISC ライセンス）。

設計の骨組みは「Piece Tree ＋ mmap／部分読み込み ＋ 疎インデックス ＋ 差分描画」で、試作（3.6）で動作と性能を確かめた。

実装した後で [基本設計.md](基本設計.md) と README に反映する。

## 1. 現状と課題

| 項目 | 現状（`vz-core::buffer`） | 問題 |
| :--- | :--- | :--- |
| 読み込み | `fs::read_to_string` で全体を `String` にし、`Vec<String>` の行に分ける | 10GB は読み込めない（メモリ不足）。UTF-8 以外はエラーになる |
| 文字コード | `encoding: &'static str` が常に `"UTF-8"` | Shift_JIS（`tmp/dir-commic.txt`、CP932・CRLF・約 2MB）を開けない |
| 描画 | `render_editor_canvas` が `lines` を前提に、折り返し・ガター・スクロールを計算する | 1 億行・1 行 50MB を想定していない |
| 検索・Grep | `SearchPattern`（`regex::Regex`）で行ごとに検索する。Grep は `read_lines` でファイル全体を読む | Grep が巨大ファイルに当たるとメモリ不足になる |

## 2. 方針（確定）

- **エンジンは 2 つ**: 基本設計メモのとおり、**通常ファイルモード**と**巨大ファイルモード**に分ける。画面側からは共通の API（`DocBuffer`、6.1）を通して両方を同じように扱う。
- **通常ファイルモード**: 今の `TextBuffer`（`Vec<String>`）のまま使う。ropey への置き換えは今回は行わない。
- **巨大ファイルモード（編集できる）**: vz-core の新しいモジュール `huge` に置き、egui には依存させない。中身は次の 3 つ。
  - 元ファイルは memmap2 でメモリに対応付ける（読み取り専用）。追加した文字は追記だけのバッファに入れる。
  - 文書は、この 2 つのバッファを指す「ピース」の並びで表す。並びは **B-Tree（Piece Tree）** で持つ（5 章）。
  - 元ファイルの行位置は、疎な行索引を裏で並列に作る。
- **自前で実装する**: Qem は使わない（3.2）。論文と Qem から借りるのは考え方だけ。
- **文字コード**: UTF-8・UTF-8 BOM・Shift_JIS を扱う処理を vz-core の新しいモジュール `encoding` に置き、両方のモードで使う。
- **追加する依存**: vz-core だけに `memmap2` `memchr` `rayon` `encoding_rs` を足す。`regex` は今のもの（`regex::bytes`）を使う。

### 3.2 Qem 1.1.0 の検証（`tmp/huge10g.txt` ほかで実測）

| 項目 | 結果 |
| :--- | :--- |
| 開く | 6ms。初回の行数確定は 3.5 秒（2 回目以降は索引キャッシュで即時） |
| 末尾の表示 / 50MB の行の切り出し | 0.16ms / 2〜5ms |
| 検索（次・前）/ 全件の走査（131 件） | 0.2ms・1.2ms / 14.5 秒 |
| 挿入 / Undo / 10GB の保存 | 25ms / 即時 / 7 秒 |
| メモリ | プライベートのピークは 150〜170MB |
| **不具合** | **索引キャッシュ（`.qem.lineidx`）を使って開き直した後に挿入すると、指定した行ではなく先頭行に書き込まれる**（300 万行・2,000 万行で再現。10GB では 5,000 万行目への挿入が 1,900,545 行目に入った）。キャッシュを無効にする設定は無い |
| 副作用 | 元のファイルの横に `.<名前>.qem.lineidx` と一時ファイルを作り、残す |
| 規模 | 約 4.8 万行（テストを除くと約 3.1 万行）。`unsafe` 8 か所、テスト以外の `.unwrap()` 67 か所 |

借りる考え方は次の 4 つ。
- mmap と、遅延して作る行索引。
- 表示する範囲だけを読む。
- 編集したらピース構造に切り替える。
- 一時ファイルへ順に書き出してから置き換える保存。

**目標値**: 速さは上の実測と同程度、メモリは 64MB 以内を目指す。

### 3.3 論文（Crowley 1998）から採るもの

| 論文の内容 | 本設計での使い方 |
| :--- | :--- |
| ピーステーブルは、読み取り専用の file buffer と追記だけの add buffer を、ピース記述子（どちらのバッファか・開始位置・長さ）でつなぐ（6.4 節） | 元ファイルの mmap と追加ブロックの列（3.4）を、`Piece { src, start, len }` でつなぐ |
| 挿入するとピースが 2 個、削除すると 1 個増える。長さ 0 のピースは消す | `insert` / `delete` の分割規則（5.5） |
| 同じ位置に続けて入力した文字は 1 個のピースにまとめる | 直前の挿入ピースの末尾が 追加ブロックの末尾と同じなら、そのピースを伸ばす |
| バッファは書き換えないので、Undo はピース記述子を取っておくだけでよく、回数の制限も不要 | 逆操作を記録する Undo（5.6） |
| 事前処理なしで開ける。メモリ量はファイルの大きさではなく、編集の回数で決まる | open は対応付けと判定だけ。行索引は裏で作る（行番号の扱いは論文の範囲外なので自前で設計） |
| 文字の参照は極めて局所的（直前の参照から 1 文字以内が 97% 以上）。そこで「指定位置から始まる最長の連続範囲（span）を返す」キャッシュで、配列並みの速さになる（8.2 節） | `span_at(pos) -> &[u8]` と、直前に参照した葉のキャッシュ（5.4） |
| 編集を重ねてピースが増えたら、記述子の並びを 2 段階の構造で持つ（7.1 節） | **ピースの並びを B-Tree で持つ**（5.2） |
| 要素が動かないので、内容を指す位置（sticky pointer）を作りやすい | 検索の行マークなどを将来ピースに結び付けられる（今回は対象外） |

### 3.4 vis（ピースチェーン）から採るもの

vis はピースを双方向リストで持ち、ピースの位置を先頭からたどって探す（O(ピース数)）。本設計では並びを B-Tree にし、それ以外の仕組みを採る。

| vis の仕組み | 本設計での使い方 |
| :--- | :--- |
| Block: 元ファイルは mmap（`BLOCK_TYPE_MMAP_ORIG`）、追加分は 1MB（`BLOCK_SIZE`）の固定ブロック。足りなければ `max(長さ, 1MB)` で新しいブロックを作る | 追加バッファを 1MB の固定ブロックの列にする（`Vec<Vec<u8>>`。確保した後に伸ばし直さないので、バイト位置が変わらない） |
| `TextChange { old: Span, new: Span, pos }`。`span_swap` は外側のつなぎだけを書き換え、古いピースは捨てない | `Change { pos, old: Vec<Piece>, new: Vec<Piece> }`。B-Tree で `pos` から始まる old のピース列を new に置き換える `replace_run` が `span_swap` に当たる。Undo / Redo はこの逆と順 |
| `Revision`（変更のまとまり）と `text_snapshot`。snapshot は今のまとまりを閉じるだけで、次の変更が来たときに新しいまとまりを作る | 同じ。キー操作 1 回（続けて入力した文字はまとめて 1 回）ごとに snapshot する |
| `cache_insert`: 直前に挿入したピースがブロックの末尾で終わり、同じまとまりの中で同じ位置に続けて入力したら、ピースを伸ばすだけで済ませる | 同じ（試作で、1,000 文字続けて入力してもピースは増えなかった） |
| Revision の木（`earlier` / `later` と時刻）で、枝分かれした履歴をたどれる | 今回は直線の Undo / Redo だけにする。木で持つことは、「時刻で戻す」機能を作るときに検討する |
| 行番号は 1 か所のキャッシュから前後に数える | 使わない。B-Tree の各節が改行数の合計を持つので、O(log n) で求まる |
| 保存: 既定は「一時ファイル `.<名前>.vis.XXXXXX` に書き、fsync して rename」（原子的保存）。シンボリックリンクとハードリンク（リンク数 > 1）では、同じファイルに書き戻す方式に切り替える | 原子的保存を既定にする。リンクの扱いは B7 |
| 読み込み: 64MB 未満は read してメモリに、それ以上は mmap | しきい値 128MB で、未満は `TextBuffer`、以上は mmap（A1） |

### 3.5 案 B1〜B7 への回答（2026-11-26 確定）

| :--- | :--- | :--- | :--- |
| B1 | 索引ができる前の編集 | **すぐ編集できる**。索引ができた範囲は編集でき、索引の範囲外の位置は索引が届くまで待つ | 改行数が未確定のピースを持てるようにする（5.2・5.3・5.5） |

文字コードは UTF-8・UTF-8 BOM・Shift_JIS の 3 つとする（A7、2026-11-26 に再確認）。

### 3.6 試作による確認（`tmp/piece_proto`、2026-11-26）

本体には組み込まず、単独のプログラムで要の部分を作って確かめた。行数は約 900 行で、内訳は `index.rs`（疎インデックス）、`tree.rs`（B-Tree）、`doc.rs`（mmap・追加ブロック・編集・Undo・保存）、`main.rs`（試験）。

**正しさ**
- **モデルとの突き合わせ**: 4 つの条件で計 6,000 回のランダムな操作を行った。条件は節の上限 4 / 8 / 32 と、索引のチャンク 512B〜1MB の組み合わせ。操作は挿入・続けての入力・最大 5 万バイトの削除・snapshot・Undo・Redo。毎回の操作の後に、次をすべて検査して通った。
  - 木の構造: 合計値、節の大きさ、葉の深さがそろっていること。
  - 内容が `Vec<u8>` のモデルと同じこと。
  - 行数と、ランダムに選んだ行の行頭が同じこと。
  - 最後に全部 Undo すると、元ファイルに戻ること。
- **保存**: 対応付けたままの元ファイルに、一時ファイルを rename で置き換えられた。その後の Undo と再保存も正しく、一時ファイルは残らなかった。

### 3.7 「Piece Tree ＋ mmap／部分読み込み ＋ 疎インデックス ＋ 差分描画」の検討

4 つを組み合わせる考え方は妥当で、本設計の骨組みとして採る。試作の結果から、要素ごとに次のように扱う。

| 要素 | 評価 | 本設計での扱い |
| :--- | :--- | :--- |
| Piece Tree | ◎ 編集は 1 回 0.35ms、2 万回の編集でも深さ 4。ピースの数が増えても、vis のリストのように遅くならない | B-Tree（5.2）。各節に (ピース数, バイト数, 改行数) を持たせ、位置からも行番号からも O(log n) で探す |
| mmap | ◎ 開くのが速く、読んだ部分だけがメモリに載る（ワーキングセットは OS が管理し、プライベートメモリには数えられない）。対応付けたままでも保存の rename ができる | memmap2 の `Mmap::map`（読み取り専用）。詳しくは 5.10 |
| 部分読み込み | ○ mmap が部分読み込みの役目を果たすので、自前の読み込みキャッシュは要らない。mmap できない場合（一部のネットワークドライブなど）の代わりの手段は要る | mmap に失敗したら、`File::read_at` で 4MB 単位に読み、最大 16 個まで覚える方式に切り替える（5.10） |
| 疎インデックス | ◎ 10GB で 1.2MB、作成 0.9 秒。元ファイルは書き換えないので、編集しても作り直さなくてよい | 元ファイルのピースを分けるときに改行数を求めるのに使う（5.3）。編集後の行番号は B-Tree の合計値から求める |
| 差分描画 | △ egui は毎フレーム画面全体を描き直す方式（immediate mode）で、変わった所だけを GPU に描かせることはできない。一方、60 行の取得は 0.3〜0.4ms（16ms の 2〜3%）で、取得は描画の妨げにならない | 「差分」は次の 2 つと読み替える（6.3）。(1) 再描画は入力・索引・検索・保存の進み具合があったときだけ頼む（egui の reactive モード。毎フレームは描かない）。(2) 表示行の文字列（デコードとタブの展開をした後のもの）を、(文書の revision, 行) をキーに覚えておき、編集した行より後だけを取り直す。文字の配置（galley）は egui が同じ文字列ならキャッシュする |

## 4. 文字コード（`vz-core::encoding`、新規）

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Default)]
pub enum TextEncoding { #[default] Utf8, Utf8Bom, ShiftJis }

impl TextEncoding {
    pub const ALL: [Self; 3];
    pub fn label(self) -> &'static str;                  // "UTF-8" / "UTF-8 BOM" / "Shift_JIS"
    pub fn detect(bytes: &[u8]) -> Self;                 // BOM → UTF-8 として正しい → それ以外は Shift_JIS
    pub fn decode(self, bytes: &[u8]) -> Cow<'_, str>;   // 不正なバイトは U+FFFD
    pub fn encode(self, text: &str) -> Result<Cow<'_, [u8]>, EncodeError>; // 表せない文字の位置を返す
    pub fn bom(self) -> &'static [u8];
}
impl fmt::Display for TextEncoding { /* label() */ }

/// 文字コードを変えながら順に書き出す（巨大ファイルの保存で使う）。
pub struct Transcoder { /* encoding_rs の Decoder / Encoder */ }
```

**判定**
- 先頭が `EF BB BF` なら `Utf8Bom`。
- 全体が UTF-8 として正しければ `Utf8`。巨大ファイルは先頭 1MB だけを見て、末尾で切れた文字は許容する。
- それ以外は `ShiftJis`。encoding_rs の `SHIFT_JIS` は CP932 相当。

**通常ファイルモードでの使い方**
- `TextBuffer.encoding` の型を `TextEncoding` にする。
- `read_lines` は中で文字コードを判定してデコードする。これで Grep と復元時の差分比較も Shift_JIS に対応する。
- 文字コードも返す `read_document` を追加する。
- `save_to_path` は `encode` した結果に BOM を付けて書く。
- `same_as_disk` はデコードした内容で比べる。

**保存するときに文字コードを変える（A7）**
- 入口は 2 つ。
  - メニュー「ファイル → 文字コードを指定して保存…」。キーは割り当てないので、キー対比の変更は不要。
  - ステータスバーの文字コード表示のクリック。
- 小さいダイアログで UTF-8・UTF-8 BOM・Shift_JIS から選び、選んだ文字コードで上書き保存する。名前を変えるときは、続けて「名前を付けて保存」を使う。
- 選んだ文字コードで表せない文字があれば保存しない。ダイアログに最初の位置（行・桁）を表示する。
- 普通に保存したとき、今の文字コードで表せない文字があれば、エラー「Shift_JIS で保存できない文字があります（文字コードを指定して保存で UTF-8 に）」を出す。
- 巨大ファイルは保存処理（5.7）が `Transcoder` を通して順に変換する。

## 5. 巨大ファイルエンジン（`vz-core::huge`、新規）

### 5.1 定数

| 定数 | 値 | 用途 |
| :--- | :--- | :--- |
| `HUGE_FILE_THRESHOLD` | 128MB | これ以上は巨大ファイルモード |
| `INDEX_CHUNK` | 16MB | 行索引を作るときの分割単位（行の境界にそろえる） |
| `SEARCH_CHUNK` | 4MB | 検索の分割単位 |
| `LINE_STRIDE` | 1024 | 元ファイルの行頭位置を何行ごとに記録するか |
| `NODE_MAX` / `NODE_MIN` | 32 / 16 | B-Tree の節の子の数（葉ではピースの数）の上限と下限 |
| `COL_STRIDE` | 4096 | 長い行で、文字位置→バイト位置の目印を何文字ごとに取るか |
| `CLIPBOARD_LIMIT` | 16MB | コピー・切り取りの上限（B4） |

### 5.2 データ構造

```rust
pub struct HugeBuffer {
    sources: Vec<Option<Source>>,// ファイルの対応付け（[0] = 開いたファイル。すべて置換の作業ファイルが続く。不要になったら None）
    blocks: Vec<Vec<u8>>,        // 追加ブロック（各 1MB 以上・確保後に伸ばし直さない。vis の Block）
    tree: PieceTree,             // ピースの B-Tree
    pub encoding: TextEncoding,
    pub line_ending: &'static str,
    pub cursor_line: usize, pub cursor_col: usize,   // TextBuffer と同じ意味（行, 文字位置）
    pub anchor: Option<TextPos>,
    pub dirty: bool, pub revision: u64,
    pub file_path: Option<PathBuf>,
    current: Vec<Change>,        // 開いている変更のまとまり（vis の Revision）
    undo: Vec<Vec<Change>>, redo: Vec<Vec<Change>>,
    last_insert: Option<InsertCache>, // vis の cache_insert
    col_cache: ColumnCache,      // 長い行の文字位置→バイト位置の目印
    save_job: Option<SaveJob>,   // 保存中（裏のスレッド）
}

struct Source {
    map: Arc<Mmap>,              // 索引・検索・保存のスレッドと共有する（読み取り専用）
    path: PathBuf,
    work_file: bool,             // すべて置換の作業ファイルなら true（不要になったら消す）
    bom_len: u64,                // BOM の分は文書に含めない
    index: LineIndex,            // 疎な行索引（5.3）
    index_rx: Option<Receiver<Vec<ChunkIndex>>>, // 作成中だけ
    cancel: Arc<AtomicBool>,
}

#[derive(Clone, Copy)]
enum Src { File(u16), Add(u32) }  // ファイルの対応付け sources[i] / 追加ブロック blocks[i]

#[derive(Clone, Copy)]
struct Piece { src: Src, start: u64, len: u64, newlines: u64, pending: bool }
// pending: 改行数がまだ分からない（索引の範囲外にかかるファイルのピース。5.3）

/// vis の TextChange: pos から始まる old のピース列を new に置き換えた記録
struct Change { pos: u64, old: Vec<Piece>, new: Vec<Piece> }
```

#### Piece Tree（B-Tree）

```rust
struct PieceTree {
    nodes: Vec<Node>,            // 節は配列に置き、番号（NodeId = u32）で参照する（Box を使わない）
    free: Vec<NodeId>,           // 空いた節の再利用
    root: NodeId,
    cache: Cell<Option<LeafHit>>,// 直前に参照した葉とその文書内の開始位置（論文の局所性キャッシュ）
}

struct Summary { pieces: u64, bytes: u64, newlines: u64, pending: u32 } // 部分木の合計（pending は改行数が未確定のピースの数）

enum Node {
    Internal { children: Vec<(NodeId, Summary)> }, // 2〜NODE_MAX 個（根以外は NODE_MIN 以上）
    Leaf { pieces: Vec<Piece> },                   // 1〜NODE_MAX 個（根以外は NODE_MIN 以上）
}
```

- **持たせる値**: 内部節は子ごとに `Summary` を持つ。葉はピースを持ち、各ピースの `newlines` から葉の合計を求める。
- **探し方**:
  - バイト位置から探すときは、`bytes` の累計で子を選びながら下りる。
  - 行番号から探すときは、`newlines` の累計で子を選びながら下りる。
  - どちらも O(log n)。ピースが 100 万個でも深さは 5 程度。
- **節が多すぎるとき・少なすぎるとき**: 子が `NODE_MAX` を超えたら半分に分け、親へ伝える。根が分かれたら木が 1 段高くなる。`NODE_MIN` を下回ったら、隣の節から借りるか、隣と合わせる。根の子が 1 つだけになったら、木を 1 段低くする。
- **Arc・Box を使わない**: 節を配列と番号で持つと、借用の問題を避けつつ `Box` や `Rc`/`Arc` が要らない（規約）。`Arc` は、裏のスレッドと共有する `Mmap` だけに使う。
- **開いた直後**: 元ファイル全体を指すピースが 1 個だけの葉 1 つ。このピースは `pending`（改行数が未確定）で、索引が完成した時点で改行数を入れる（5.3）。
- **メモリ**: ピース 1 個は 32 バイト。100 万個のピースでも約 40MB に収まる。編集しない限りピースは 1 個のまま。

### 5.3 元ファイルの行索引（バックグラウンド・並列）

1. `HugeBuffer::open` は対応付けと文字コードの判定だけを行い、すぐに返す。目標の初期表示 100ms 以内はこれで満たす。
2. 索引スレッド `vz-huge-index` が `INDEX_CHUNK` ごとに区切る。区切りは次の `\n` まで進めて行頭にそろえる。
3. 区切ったチャンクを rayon で並列に処理する。各チャンクで次の 2 つを求める。
   - `memchr_iter(b'\n')` で数えた改行数。
   - `LINE_STRIDE` 行ごとの行頭位置（`marks`）。
4. 束にした結果に先頭から通しの行番号を付け、mpsc で UI に送る。最初の束は 1 チャンクだけにして、すぐ表示できるようにする。
5. UI は毎フレーム `poll_index()` で受け取る。作成中は 100ms ごとに再描画を頼む。

```rust
struct ChunkIndex { start: u64, end: u64, first_line: u64, lines: u64, marks: Vec<u64> }
struct LineIndex { chunks: Vec<ChunkIndex>, complete: bool }
impl LineIndex {
    fn newlines_in(&self, map: &[u8], range: Range<u64>) -> Option<u64>; // 両端の行番号の差＋端の数え直し
    fn nth_line_start(&self, map: &[u8], from: u64, n: u64) -> u64;      // from から n 行先の行頭
}
```

**作成中の閲覧と編集（B1）**
- **確定と未確定**: 索引ができた範囲（ファイルの先頭から `indexed_end` まで）の改行数は確定している。範囲外にかかるファイルのピースは `pending` にする。
- **行の位置**: `pending` のピースの中でも、`indexed_end` より前の行は索引で位置が分かる。それより後の行と、`pending` のピースより後ろにあるピースの行番号は、索引が届くまで分からない。
  - 表示は確定した行まで。総行数は推定値で示し、ステータスに「索引作成中 nn%（索引ができた範囲は編集できます）」と出す。
  - 範囲外への移動（末尾へ・行ジャンプ）は、索引が届くまで待つ（`pending_jump`）。
- **編集**:
  - 編集する位置が確定した行の中にあれば、そのまま編集する。
  - `pending` のピースを分けると、前の部分（`indexed_end` より前）は改行数が確定し、後ろの部分は `pending` のまま残る。開いた直後に先頭近くを編集しても、ピースが分かれるだけ。
  - 範囲外の位置での編集は `EditError::Indexing` を返す（カーソルが範囲外に行くことは無いので、通常は起きない）。
- **索引が伸びたら**: `poll_index()` が索引を受け取るたびに、`pending` のピースのうち索引が届いたものの改行数を入れて、葉から根まで `Summary` を直す。`pending` のピースは「開いた直後の 1 個を、何回分けたか」の数しかないので少ない。Undo の履歴の中のピースは、木に戻すときに改行数を入れる。
- **すべて置換の作業ファイル（5.9）**: 書き出しながら索引を作るので、最初から完成している（`pending` にならない）。

### 5.4 読み出し

```rust
impl HugeBuffer {
    pub fn line_count(&self) -> usize;                       // 改行数 + 1（作成中は推定値）
    pub fn span_at(&self, pos: u64) -> &[u8];                // pos から始まるピース内の連続範囲（論文の span キャッシュ）
    pub fn line_byte_range(&self, line: usize) -> Range<u64>;// 行頭〜行末（\r\n を除く）の文書内バイト範囲
    pub fn line_segment(&self, line: usize, start_col: usize, max_cols: usize) -> Cow<'_, str>;
    pub fn line_char_len(&self, line: usize) -> usize;
    pub fn text_in_range(&self, start: TextPos, end: TextPos, limit: usize) -> Result<String, TooLarge>;
}
```

- **行頭の求め方**: 木を `newlines` で下り、行頭を含むピースを見つける。
  - 元ファイルのピースなら、`LineIndex::nth_line_start` でピース内の位置を求める。
  - 追加バッファのピースなら、`memchr` で数える。
  - 行がピースをまたぐときは、`span_at` を順につないで読む。
- **文字位置→バイト位置（A4）**:
  - 64KB 未満の行は、行頭からデコードして求める。
  - 長い行は `ColumnCache` が `COL_STRIDE` 文字ごとに (文字位置, バイト位置) の目印を持つ。必要な所まで前へ進めて作り、表示中の長い行だけを最大 16 行ぶん覚える。
  - 50MB の行（約 5,200 万文字）でも目印は約 1.3 万個。行の途中への横スクロールは、一番近い目印から数えるだけで済む。
- **キャッシュの捨て方**: 編集すると、その行以降の `ColumnCache` を捨てる。木の `cache` は、編集のたびに捨てる。

### 5.5 編集（論文 6.4 節の規則を Piece Tree で行う）

```rust
impl HugeBuffer {
    pub fn insert_text(&mut self, text: &str) -> Result<(), EditError>;     // 選択中は置き換え
    pub fn delete_range(&mut self, start: TextPos, end: TextPos) -> Result<(), EditError>;
    // 移動・選択・Undo などは TextBuffer と同じ名前と意味（6.1）
}
enum EditError { Indexing, Unencodable { ch: char }, Saving, TooLarge }
```

**挿入**
1. 文字列をファイルの文字コードに変換して 追加ブロックの末尾に足す（足りなければ新しいブロックを作る）。表せない文字があれば `Unencodable` を返し、ステータスで「文字コードを指定して保存」を案内する。
2. 挿入位置を含むピースを、(前・新しいピース・後) の 3 つに分ける。ピースの境界に挿入するときは、新しいピースを 1 つ足すだけ。
3. 同じ位置に続けて入力した場合は、ピースを増やさない。直前のピースが Add で、その末尾が ブロックの末尾と同じなら、そのピースの `len` を伸ばす。

**削除**
- 範囲にかかる両端のピースを切り詰め、間のピースを木から外す。1 つのピースの中だけを削除するときは、2 つに分ける。

**改行数の更新**
- 分けたピースの改行数は、ファイルのピースなら `LineIndex::newlines_in`、追加ブロックのピースなら `memchr` で数える。索引の範囲外にかかる部分は `pending` にする（5.3）。
- 変わった葉から根までの `Summary` を直す。
- 1 回の編集の計算量は O(log n + 改行を数える量)。

**索引が完成するまで**: 確定した行の中なら編集できる。範囲外の位置は `Indexing` を返す（B1、5.3）。

### 5.6 Undo / Redo（vis の Change / Revision 方式）

- 編集ごとに `Change { pos, old, new }` を今のまとまり（`current`）に足す。バッファは書き換えないので、ピースを取っておけば元に戻せる（論文・vis）。
- **まとまりを閉じる**: キー操作の区切りで `snapshot()` を呼び、`current` を Undo の積み上げに移す（vis の `text_snapshot`）。新しく編集してまとまりを閉じたら、Redo の積み上げは捨てる。
- **Undo**: まとまりの中の変更を新しい順に、`pos` から始まる new のピース列を old に置き換える（`replace_run`。vis の `span_swap` に当たる）。
- **Redo**: 古い順に、old を new に置き換える。
- **続けて入力した文字**: 1 つのピースを伸ばすだけにする（`last_insert`。vis の `cache_insert`）。snapshot・削除・カーソル移動で解除する。
- 回数は 200 回まで（B5）。超えたら一番古いまとまりを捨てる。保存しても履歴は残す（B6）。
- **ファイルの対応付けを片付ける**: 履歴を捨てたとき、バッファを閉じたとき、ピース数を減らすために対応付け直したとき（5.7）に、どのピース（木と履歴の中）からも指されなくなった `sources[i]` を `None` にする。これで対応付けが外れ、作業ファイルなら消す。参照は、木と履歴 200 件を走査して数え直す（ピースが数万個でも数 ms）。
- 永続木（パスコピー）は使わない。使うと `Arc` が必要になり、ピース数に比例したメモリも増えるため。

### 5.7 保存（裏のスレッドで順に書き出し、置き換える）

1. 保存先と同じフォルダに一時ファイル `.<名前>.vzsave.tmp` を作る。作業ファイルは保存先のフォルダにしか作らず、元ファイルの横に残すこともない。
2. 保存スレッド `vz-huge-save` が、ピースを先頭から順に書き出す。
   - 文字コードを変えるときは、`Transcoder` を通す。BOM はここで付けるか外す。
   - 書きながら改行を数え、新しいファイルの行索引をその場で作る。
3. 保存中は編集できない（`EditError::Saving`）。閲覧はできる。ステータスに進み具合（バイト）を出す。
4. 書き終えたら `sync_all` を呼び、一時ファイルを保存先に置き換える（`std::fs::rename`）。元ファイルの mmap は外さない。Windows でも置き換えられ、古い対応付けからは元の内容を読み続けられる（3.6 で確認。Rust 1.100 の rename は POSIX 方式）。
5. ピースはそのまま（古い対応付けと追加ブロックを指したまま）にして、Undo の履歴を残す（B6）。保存後に Undo すると、未保存の状態に戻る。
   - 古い対応付けの元ファイルは、ディスク上では名前の無いファイルとして残る。この文書を閉じるまで、その分のディスク容量を使い続ける。
   - 次に開いたとき、またはピースが増えすぎたとき（例: 10 万個）に、保存したファイルを対応付け直して、ピースを 1 個にする。この時点で Undo の履歴は消す。
6. 失敗したとき（空き容量不足など）は、一時ファイルを消し、編集中の状態をそのまま残してエラーを表示する。置き換える前に失敗した場合、元ファイルには触れない。
7. 「名前を付けて保存」でも同じ手順を使う。保存した後は、新しいパスのファイルを開いている状態になる。

### 5.8 検索（非同期・キャンセル可能・並列）

```rust
pub enum Matcher { Bytes(regex::bytes::Regex), Decoded(regex::Regex, TextEncoding) }
impl Matcher { pub fn new(pattern: &SearchPattern, encoding: TextEncoding) -> Result<Self, String>; }
pub fn find(doc: &DocSnapshot, m: &Matcher, from: u64, up: bool, wrap: bool, cancel: &AtomicBool) -> Option<Range<u64>>;
```

**正規表現の作り方**
- `SearchPattern` に、元の正規表現の文字列と、大文字・小文字を区別するかを持たせる。
- `regex::bytes` を `multi_line(true)`・`crlf(true)` で作る。単語境界 `{start-half}` などもそのまま使える。

**読み出し**
- 文書を、行の境界にそろえた約 `SEARCH_CHUNK` ずつに分けて読む。
- 1 つのピースの中に収まる範囲は、mmap や追加ブロック をそのまま参照する。複数のピースにまたがる範囲だけ、一時的な `Vec<u8>` にコピーする。

**照合**
- UTF-8 はバイト列のまま照合する。
- Shift_JIS はデコードしてから照合する。一致した位置は、行頭までを Shift_JIS に戻した長さでバイト位置に換算する。Shift_JIS の 2 バイト目に `0x0A` は来ないので、行の境界で分けても文字は壊れない。
- 改行をまたぐ一致は捨てる。
- チャンクをスレッドの数ずつ並列に調べる。下検索は最初の一致を、上検索は最後の一致を採る。

**裏のスレッドとの受け渡し**
- `DocSnapshot` は、検索スレッドに渡すピース列の写し。編集の回数ぶんの大きさしかない。中身は `Arc<Mmap>` と、追加ブロックの写し（入力した量の分。確保後に伸ばし直さないので、使い終わったブロックは共有できる）。
- 検索中に編集したら、その検索は中止する。
- 結果のバイト位置は、UI 側で木を使って (行, 文字位置) に直す。

**Grep（`vz-core::grep`）**
- 保存されたファイルが対象なのは変わらない。
- ファイルの大きさが `HUGE_FILE_THRESHOLD` 以上なら、`read_lines` は使わない。mmap を同じ方法で並列に走査し、行番号と桁を求める。
- 結果の上限 2,000 件と、中止はそのまま。

### 5.9 すべて置換（B3）

一致の数だけピースを増やすと、1 億件の置換でピースが 1 億個を超える。そこで、置換した結果を作業ファイルに書き出し、文書をその 1 ピースに入れ替える。

1. **始める前の確認**: 置換後の文字列をファイルの文字コードに変換できるか確かめる。Shift_JIS で表せない文字があれば、始めずにエラーにする。
2. **書き出し**: 置換スレッド `vz-huge-replace` が、`DocSnapshot`（5.8）を行の境界にそろえたチャンクごとに読み、置換しながら作業ファイルに書き出す。
   - 作業ファイルは `.<名前>.vzwork-<番号>.tmp` で、開いたファイルと同じフォルダに作る。同じフォルダにする理由は、保存のときに rename で置き換えられるようにするため。
   - UTF-8 は `regex::bytes::Regex::replace_all` で置換する。Shift_JIS は、デコードして置換し、エンコードし直す。
   - 置換の範囲が選択範囲だけ（今の「選択範囲のみ」）なら、範囲の外はそのまま写す。
   - 書きながら、作業ファイルの行索引と置換した件数を求める。
3. **書き出し中**: ステータスに進み具合と件数を出す。Esc か「中止」で止められ、止めたら作業ファイルを消す。この間は編集できない（`EditError::Saving` と同じ扱い）。閲覧はできる。
4. **入れ替え**: 書き終えたら、作業ファイルを `sources` に足して対応付ける。文書の全ピースを、作業ファイル全体を指す 1 個のピースに置き換える。
   - この置き換えは `Change { pos: 0, old: 全ピース, new: [1 個] }` として、1 回の Undo 単位にする。Undo すると置換前に戻り、Redo すると置換後に戻る。
   - 件数が 0 なら、入れ替えずに作業ファイルを消す。
5. **保存**: 文書が「作業ファイル全体を指す 1 個のピース」のままで文字コードも同じなら、作業ファイルを `sync_all` してから保存先へ rename するだけで済ませる（書き出しが要らない）。それ以外は 5.7 の通常の保存を使う。
6. **片付け**: 作業ファイルを指すピースが無くなったら、対応付けを外して消す（5.6）。異常終了で残った作業ファイルは、次に同じファイルを開いたときに消す（消せなければ放っておく）。
7. **空き容量**: 作業ファイルには文書と同じくらいの空き容量が要る。書き込みに失敗したら作業ファイルを消し、エラーを表示する（文書は変わらない）。

### 5.10 mmap と部分読み込み（memmap2）

- **元ファイル**: `File::open` してから `unsafe { Mmap::map(&file) }` で、読み取り専用に対応付ける。
  - `unsafe` が要る理由: 対応付けている間に、ほかのプロセスがファイルを書き換えたり切り詰めたりすると、内容が変わったり、読み取りで異常終了（Unix の SIGBUS）したりしうる。
  - 対策:
    - Windows は、対応付け中のファイルを切り詰められない。
    - Unix は、外部での変更の検知（更新日時とサイズ。6.2）で変わったと分かったら、すぐ対応付けを外して開き直すかを尋ねる。
    - `map_if_safe`（内容が変わらないと保証できるときだけ対応付ける）は、通常のファイルでは使えないので採らない。
- **アクセスの仕方を OS に伝える（Unix だけ）**: `Mmap::advise`（`Advice::Sequential`）で、索引作成・検索・保存のように先頭から順に読むことを伝える。表示のとびとびの読み出しには `advise_range` で `Advice::Random` を使うかを、ベンチで決める。Windows には対応する API が無いので呼ばない（`#[cfg(unix)]`）。
- **追加ブロック**: 通常の `Vec<u8>`（1MB 以上の固定容量）にする。`MmapMut::map_anon` は、ページ単位の確保になる割に利点が無いので使わない。
- **部分読み込みへの切り替え**: `Mmap::map` が失敗したとき（一部のネットワークドライブ、特殊なファイルなど）は、元ファイルを `PartialReader` で読む。`File::read_at`（Windows は `seek_read`）で 4MB 単位に読み、最大 16 個（64MB）まで覚えておく。`Original` の中で振り分けるので、木や編集の処理は変わらない。
- **巨大ファイルモードでないとき**: 128MB 未満は、今までどおり `TextBuffer` が全体を読み込む。

## 6. 画面・操作（vz-ui）

### 6.1 共通 API `DocBuffer`（基本設計メモの「共通 TextBuffer API」）

```rust
// vz-core::doc（新規）。dyn や Box を使わず、列挙型で振り分ける
pub enum DocBuffer { Text(TextBuffer), Huge(HugeBuffer) }
impl DocBuffer {
    // 読み出し: line_count / line_char_len / line_segment / line_text(短い行) / text_in_range
    // カーソル・選択: cursor_pos / set_cursor / move_* / anchor / selection_range / select_*
    // 編集: insert_text / insert_newline(_with_indent) / backspace / delete_char_at_cursor /
    //       delete_range / delete_current_line / duplicate_line / overwrite_text -> Result<(), EditError>
    // Undo: undo / redo / can_undo / can_redo
    // 状態: dirty / revision / file_path / encoding / line_ending / display_name / is_markdown
    pub fn as_text(&self) -> Option<&TextBuffer>;   // 巨大ファイルでは未対応の機能（Markdown・全置換など）用
}
```

- `BufferSlot.buffer` の型を `DocBuffer` にする。`cur_buf()` は `&DocBuffer` を返す。
- **`lines` を直接使っている箇所を置き換える**: vz-ui で約 36 か所（search 10、restore 7、wrap 4、editor_view 3、mod 3 など）。`line_count()`・`line_segment()`・`line_text()` に置き換える。
  - `line_text` は短い行だけ `Cow::Borrowed` を返す。長い行には `line_segment` を使う。
  - 通常ファイルモードの `line_segment` は、`lines[i]` の部分を借りるだけなので遅くならない。
- **編集の失敗**: 編集の関数は `Result` を返し、`EditError` はステータスバーに表示する。通常ファイルモードは常に成功する。
- **巨大ファイルでは使えない機能**: Markdown ビュー・行マーク（B3）は、`as_text()` が None のとき「巨大ファイルでは未対応」と表示する。
- `SearchPattern::find(&TextBuffer)` は通常ファイルモード用として残す。巨大ファイルは 5.8 の非同期検索に分ける。

### 6.2 開く・閉じる・外部変更

- `open_file_in_buffer`: `fs::metadata().len() >= HUGE_FILE_THRESHOLD` なら `HugeBuffer::open` を使う。ステータスは「巨大ファイルを開きました（索引作成中）」。
- 閉じる・終了時の保存確認は、今の流れをそのまま使う。保存は 5.7 の非同期の保存で、保存中に終了しようとしたら完了を待つ。
- 外部での変更の検知は、巨大ファイルでは更新日時とサイズを比べるだけにする。差分を比べるために読み直すことはしない。変わっていたら「再読み込み」と「無視」を尋ねる。再読み込みすると、編集内容は捨てて開き直す。
- `--save-and-quit` / `--restore` は B2 の方法を使う。

### 6.3 描画

- `render_editor_canvas` を `DocBuffer` で描けるようにする。
  - 表示する行は `line_segment(行, 横スクロールの文字位置, 画面に入る文字数)` で取る。
  - ガターの行番号は最大 10 桁にする。
  - スクロールバーは「表示中の行 ÷ 総行数」で描く。作成中は推定の総行数を使う。
- **折り返し（A5）**:
  - 通常ファイルモードは、今の `WrapLayout`（全行の行割り）を使う。
  - 巨大ファイルは `LazyWrap` を使う。基準は (論理行, 行内の表示行番号) で、画面に入る範囲だけを折り返して覚える。
  - 長い行では、表示行ごとの開始位置を `ColumnCache` と同じ間隔で目印にする。
  - 折り返し中のスクロールバーは論理行の割合で描く。行ジャンプの「表示行で指定」は巨大ファイルでは使えないので、論理行として扱う。
- 先頭で `ui.multiply_opacity(window_style::text_alpha())` を呼び、背景は `bg_painter()` で塗る（規約）。
- **差分描画（3.7）**:
  - 再描画を頼むのは、入力があったとき、または索引の作成・検索・保存が進んだときだけ（100ms ごと）。何も起きていなければ描かない。
  - `RowCache` は、表示行の文字列（デコードとタブの展開をした後のもの）を、(行, 横の開始文字位置) をキーに覚える。編集すると、変わった行より後だけを捨てる（編集は、変わり始めた行と行数の増減を返す）。スクロールでは、新しく画面に入った行だけを取る。
  - 文字の配置（galley）の作り直しは、egui が同じ文字列ならキャッシュする。
  - 試作では、行の取得は 1 フレーム 0.3〜0.4ms だった。`RowCache` は、描画全体を測って必要だと分かったときに入れる（最初は入れない）。

### 6.4 キー操作

- **キーの割り当ては変えない**。サクラ互換・VZ 互換の今の処理が `DocBuffer` を通して両方のモードで動く。キーの追加は無いので、キー対比と F1 は「巨大ファイルの制限」を書き足すだけ。
- 巨大ファイルでの違いは次の表のとおり。

| 操作 | 巨大ファイルでの動作 |
| :--- | :--- |
| 移動・選択・入力・削除・貼り付け・Undo | 通常と同じ（索引の作成中は、索引ができた範囲で編集できる: B1。保存中・すべて置換の書き出し中は編集できない）。Undo は 200 回まで（B5） |
| コピー・切り取り | 16MB まで（B4） |
| 検索・次・前 | 非同期で検索し、見つかったら選択する。もう一度押すか Esc で中止する |
| 1 件ずつの置換 | できる |
| すべて置換 | 裏のスレッドで作業ファイルに書き出し、1 ピースに入れ替える。進み具合と件数を表示し、中止できる。Undo 1 回で戻る（5.9） |
| 行マーク | 未対応（B3） |
| 行ジャンプ | 論理行で移動する（索引の範囲外なら、届くまで待つ） |
| Markdown ビュー | 未対応 |

### 6.5 ステータスバー

- 巨大ファイルは `Ln {行}/{総行数}  Col {桁}` の後に `[巨大]` を付ける。
- 状況に応じて「索引 nn%」「検索中…」「保存中 nn%」を出す。
- 文字コードの表示をクリックすると、文字コードを選ぶダイアログ（4 章）を開く。

### 11.2 設計と変えたところ

- **共通 API**: 6.1 の列挙型 `DocBuffer` ではなく、`TextBuffer` の中身を切り替える形にした。画面側の `TextBuffer` の使い方（公開しているフィールドと約 50 の関数）を変えずに済み、変更は `lines` を直接使っていた箇所の置き換えだけで済んだ。
- **Undo の単位**: 巨大ファイルでは、続けて入力した文字を 1 回の Undo にまとめる（vis と同じ）。通常ファイルモードは今までどおり 1 文字ずつ。
- **横スクロール**: ピクセル単位ではなく文字単位にした。ピクセル単位では、全角を含む行で文字位置と表示位置がずれ、行が空に見える不具合が出た（実機で確認して直した）。
- **差分描画の `RowCache`**: 入れていない。実測で 1 フレームの行の取得が 0.3〜0.4ms と小さかったため（3.7）。

## 12. 未実装の項目の対応方針（案・2026-11-26 検討）

11.3 の項目ごとに、やり方と規模、勧める順序を書く。いずれも**案**で、確認してから実装する。

### 12.1 巨大ファイルの折り返し表示（A5）

**難しいところ**
- 今の `WrapLayout` は全行の折り返し位置（`breaks`）と、各行の先頭の表示行番号（`row_start`）を持つ。1 億行では、作るのに全文のデコードが要り、メモリも数 GB になる。
- 1 行 50MB の行は約 40 万表示行になる。行の途中を表示するたびに行頭から数え直すと、1 フレームに収まらない。

**案 A: 表示範囲だけを折り返す（勧める）**
- 縦の位置を「先頭に表示している (論理行, 行内の表示行)」で持つ（`slot.huge_wrap_top`）。ピクセル単位の `scroll_y` は使わない。
- 毎フレーム、先頭の論理行から画面に入る分だけ（前後に少し余分を足して）折り返し、**窓の分だけの `WrapLayout`**（論理行の番号を窓の先頭からの差にしたもの）を作る。描画・クリック・選択の処理は、今の `row_to_line` / `seg_range` / `is_last_seg` をそのまま使える。
- **長い行**: 折り返し位置の目印を、`col_cache` と同じように一定の表示行ごと（例: 4,096 表示行ごと）に (表示行, 文字位置) で覚え、表示中の長い行だけを数行ぶん持つ。行の途中の表示行へは、一番近い目印から数える。
- **操作**
  - 上下の移動・ページ移動は、カーソル行と隣の行の折り返しだけを計算する（今の `move_cursor_row` の巨大ファイル版）。
  - ホイールは先頭位置を表示行単位で前後へ動かす。
  - カーソルが画面外に出たら、カーソルの表示行を先頭位置にするか、画面の高さぶん前へ戻した位置を先頭にする。
- **スクロールバー**: 論理行の割合で描く（先頭の論理行 ÷ 総行数）。つまみを動かすと、その論理行の最初の表示行へ移る。
- **行ジャンプの「折り返し単位」**: 巨大ファイルでは使えないようにする（総表示行数が分からないため）。
- **編集**: 編集した行より後の目印を捨てる（`col_cache` と同じ）。
- **規模**: wrap.rs に約 300 行、editor_view.rs の分岐。メモリはほぼ増えない。

**案 B: 全体の折り返し索引を裏で作る**
- 行索引と同じく、1,024 論理行ごとの表示行の累計を裏のスレッドで作る。これがあれば、総表示行数・正確なスクロールバー・表示行でのジャンプが使える。
- 欠点:
  - ウィンドウの幅や文字の大きさを変えるたびに、全体を作り直す必要がある（10GB で数秒〜十数秒）。
  - 編集のたびに、後ろの累計を直す必要がある（ブロックごとの差分を Fenwick 木で持てば O(log n)）。
- 案 A で困ることが出てから検討する。

### 12.2 mmap できないときの読み込み（5.10）

- **案（勧める）**: `Source` の中身を `enum { Mapped(Arc<Mmap>), Heap(Arc<Vec<u8>>) }` にする。mmap に失敗し、ファイルが上限（例: 物理メモリの 1/4、かつ 2GB 以下）より小さければ、全体をメモリに読み込む。どちらも `&[u8]` を返せるので、木・索引・検索・保存の処理は変わらない。上限を超えるときは、今と同じく理由を表示して開かない。
- **設計時の案（4MB 単位の部分読み込み）**は、`bytes()` が借用を返せなくなり、ほぼすべての読み出しに手が入る。そのため採らない。
- まず、Windows で mmap が失敗する場面（OneDrive のオンデマンドのファイル、ネットワークドライブなど）を実際に確かめる。
- **規模**: 小（`huge/mod.rs` で約 50 行）。

### 12.3 保存して終了で保存できなかったときの編集内容（B2）

- **案**: 編集内容（ピース列と、使っている追加ブロック）と元ファイルの状態（更新日時・サイズ）を、セッションのフォルダに `huge-<番号>.vzedit` として書く。`session.ini` に新しい種類（例: `EntryKind::HugeEdits`）を足す。
- `--restore` のときは元ファイルを開き直し、状態が同じならピース列を当て直す（Undo の履歴は戻らない）。違えば当て直さず、「元ファイルが変わったため、未保存の編集を戻せませんでした」と表示し、`.vzedit` はセッションのフォルダに残す。
- すべて置換の作業ファイルを指すピースがあるときは、作業ファイルもセッションのフォルダへ移すか、その場合は一時保存しない（保存を勧める表示）。後者を勧める。
- **規模**: 中（vz-core に書き出しと読み込みで約 150 行、vz-config の `session` に種類を 1 つ、`restore.rs`）。保存に失敗することは少ない（空き容量不足くらい）ので、優先度は低い。

### 12.4 ハードリンクへの保存の確認（B7）

- **案**: vz-platform に `hard_link_count(path) -> Option<u64>` を足す。Unix は `MetadataExt::nlink()`、Windows は `GetFileInformationByHandle` の `nNumberOfLinks` を使う。
- 巨大ファイルの保存の前に 2 以上なら、「ハードリンクが切れます（このファイルだけが新しい内容になります）。保存しますか？」と確かめる。
- 通常ファイルモードは同じファイルに書き戻す（`fs::write`）のでリンクは切れず、確認は要らない。
- **規模**: 小（約 60 行と確認画面）。

### 12.5 すべて置換の結果を rename だけで保存する

- **案**: 保存の前に `HugeDoc::whole_work_file()` で、文書が作業ファイル全体を指す 1 個のピースだけかを調べる。そうで、保存する文字コードに BOM が無く変換も要らなければ、作業ファイルを `sync_all` してから保存先へ rename する。その後は、その対応付けを作業ファイルではない元ファイルとして扱う（`work_file = false`、`path` を保存先に）。
- BOM が要るときや文字コードを変えるときは、今どおり全体を書き出す。
- **規模**: 小（約 40 行）。効果は、10GB の保存が約 3 秒から 1 秒未満になり、空き容量も文書 1 つ分少なくて済むこと。

### 12.6 検索の Esc での中止

- **案**: 巨大ファイルの検索（`huge_find`）・すべて置換（`huge_replace`）の実行中だけ、エディターの Esc を「中止」にする。ステータスに「検索を中止しました」と表示する。実行中でなければ、今どおりファイラーへ切り替える。
- 両方式で同じ扱いにし、キー対比・README・F1 にも書く（キー操作の変更にあたるため）。
- **規模**: 小（約 20 行と文書）。

### 12.7 Unix での `Mmap::advise`

- **案**: 開いたら `Advice::Random`、索引の作成中は `advise_range(Sequential)` を呼ぶ。`#[cfg(unix)]` で分ける。
- 効果は、OS のキャッシュに載っていないときの索引の作成と検索の速さ。WSL2 で冷えた状態（`echo 3 > /proc/sys/vm/drop_caches`）と比べて、効くときだけ入れる。
- **規模**: 極小。
